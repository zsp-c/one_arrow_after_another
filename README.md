# 一箭又一箭（Python + Pygame）

## 一、项目名称

**一箭又一箭**（英文名：*One Arrow After Another*）—— Python + Pygame 实现的点击解谜小游戏。

## 二、游戏简介

这是一个参考微信小游戏《一箭又一箭》**核心玩法**实现的小游戏作业。棋盘上摆着若干带方向
的箭头（上、下、左、右四种），玩家点击箭头，程序检查它前进方向上有没有别的箭头挡路：

- 前方畅通 → 箭头飞出棋盘并被消除；
- 前方有箭头挡路 → 箭头飞不出去，会被弹回来并消耗一次失误机会。

把一关的箭头全部清空即可通关进入下一关；失误次数耗尽则本关失败。

**主要特性**

- 上、下、左、右四种方向的箭头，鼠标点击操作，点击判定严格按“同一行 / 同一列、
  箭头与边界之间是否还有其他箭头”执行；
- 飞出、碰撞都有动画反馈：飞出带残影拖尾与火花，碰撞会顶出去再弹回、闪红，
  并把挡路的那支箭头用金色方框闪两下；
- 悬停任意箭头即可预览它的前进路线（绿点畅通 / 金点可走 / 红点被挡）；
- **自动提示**：每关 2 次，点了直接帮你飞掉一支能走的箭头，不消耗失误次数；
- 4 个可通关关卡，难度从 5 支箭头递增到 12 支；
- 开始界面、游戏界面、通关 / 失败结算界面，支持重新开始本关。

本项目为独立实现，**未使用原游戏的任何素材、代码或关卡数据**。

### 界面说明

游戏共三个界面：**开始界面**、**游戏界面**、**通关 / 失败结算界面**。

开始界面有「开始游戏」按钮和 4 个关卡入口，可以直接跳到任意一关。

游戏界面左侧是棋盘，右侧信息栏自上而下显示：

1. 剩余箭头数
2. 本关箭头总数与已飞出数
3. 剩余失误（红点表示还剩几次）与已失误次数
4. 本关提示文字
5. 清空进度条
6. 三个按钮：**自动提示**、**重新开始本关**、**返回主菜单**

顶部显示当前关卡序号（第 N 关 / 共 4 关）与关卡名称。
自动提示按钮上会显示剩余次数（如「自动提示（剩 2 次）」），用完或动画播放期间自动置灰。

### 辅助功能

- **路径预览**：鼠标悬停在箭头上时，它前方的路径会逐格标出来。绿色表示畅通，金色表示
  可以走到这里，红色表示被这支箭头挡住（同时红色方框标出挡路者），被挡住之后的格子变灰
  （说明无关紧要）。前方畅通时，棋盘对应的那条边上还会出现一条绿色出口。
- **自动提示**：见[第七节](#七玩法规则判定细节)。

### 结算界面

- 清空本关全部箭头 → **关卡完成**，可选择「进入下一关」或「重玩本关」；
  通关最后一关则显示**全部通关**。
- 失误次数耗尽 → **挑战失败**，可选择「重新开始本关」或「返回主菜单」。

## 七、玩法规则（判定细节）

棋盘是若干行列的网格，每个格子里最多有一支箭头，方向为上、下、左、右四种。

点击一支箭头后，程序沿它所指的方向朝棋盘边界逐格检查：

- **前方没有其他箭头** → 箭头飞出棋盘并被消除；
- **前方有别的箭头** → 箭头不能消除，会朝前顶一下再被弹回来、闪红、并冒出“被挡住了！”
  的提示，同时把挡路的那支箭头用金色方框标出来；这次点击**消耗一次失误机会**。

清空本关全部箭头即通关并进入下一关；失误次数耗尽则本关失败，可以重新开始。

> 判定口径与作业要求一致：**只看同一行或同一列、箭头与边界之间还有没有其他箭头**，
> 不涉及其他机关。基础版采用网格中的单格箭头。

### 自动提示

每关有 2 次提示机会。点击侧栏的「自动提示」按钮（或按 `H`），程序会自动找出一支当前
就能飞出棋盘的箭头，**并直接替你把它点掉**——你会看到那支箭头飞出去，同时它的原位被
绿色脉冲圆环圈住、畅通的路线画成绿点，说明“为什么它能走”。

自动提示走的是和手动点击完全相同的那条代码路径，所以它**不会消耗失误次数**
（选中的箭头本来就畅通，按规则不扣失误）。

> 为什么提示选的箭头一定是对的：本关规则下，移除箭头只会解开阻挡、**永远不会制造阻挡**，
> 所以任何一支“前方畅通”的箭头点掉都不会让关卡变成死局。提示按行列顺序取第一支，
> 同一局面下结果稳定可复现。

> 提示次数可以在 `levels.py` 里用 `"hints"` 字段给某一关单独调整，
> 默认值 2 定义在 `game_logic.py` 的 `HINTS_PER_LEVEL`。

## 八、关卡设计与通关顺序

共 4 关，**全部由程序搜出顺序并逐步回放验证过**（见 `check_levels.py`）。
坐标写法为 `r行c列`，行列都从 0 开始，与 `check_levels.py` 的输出一致。

### 第 1 关 · 初识箭头（5×5，5 支箭头，失误上限 3 次）

```
      c0  c1  c2  c3  c4
  r0   ·   ·   ·   ·   ^
  r1   ·   <   ·   ·   ·
  r2   ·   ·   ·   ·   ·
  r3   ·   >   ·   v   ·
  r4   ·   ·   ·   v   ·
```

通关顺序：`r0c4`(上) → `r1c1`(左) → `r4c3`(下) → `r3c3`(下) → `r3c1`(右)

设计意图：先用两支本来就能飞出的箭头熟悉规则，再引出“r3c3 挡住 r3c1、r4c3 挡住 r3c3”
的两级连锁。本关失误给得宽松，允许试错。

### 第 2 关 · 连锁反应（6×6，8 支箭头，失误上限 3 次）

```
      c0  c1  c2  c3  c4  c5
  r0   ·   ·   ·   ·   ·   v
  r1   ·   >   ·   ·   v   ·
  r2   ·   ·   ·   ·   ·   ·
  r3   ^   ·   ·   ·   ·   ·
  r4   ^   ·   <   ·   <   ·
  r5   ·   ·   ·   ^   ·   ·
```

通关顺序：`r0c5`(下) → `r3c0`(上) → `r4c0`(上) → `r4c2`(左) → `r4c4`(左) →
`r1c4`(下) → `r1c1`(右) → `r5c3`(上)

设计意图：左下角一条“上→上→左→左→下→右”的六连链，必须从链条末端倒着拆。

### 第 3 关 · 十字路口（6×6，11 支箭头，失误上限 3 次）

```
      c0  c1  c2  c3  c4  c5
  r0   ·   ·   <   ·   ·   ·
  r1   ·   ·   ^   ·   ·   <
  r2   ·   ·   ·   v   ·   ^
  r3   ·   ·   ·   ·   ·   ^
  r4   ^   ·   ·   <   ·   ·
  r5   <   ·   ·   >   ·   ^
```

通关顺序：`r0c2`(左) → `r1c2`(上) → `r1c5`(左) → `r2c5`(上) → `r3c5`(上) →
`r4c0`(上) → `r4c3`(左) → `r5c0`(左) → `r5c5`(上) → `r5c3`(右) → `r2c3`(下)

设计意图：最右列叠了四层（r1c5 → r2c5 → r3c5 → r5c5），中间还夹着一条独立的
“r4c0 → r4c3 → r2c3”链，两条链互不干扰但容易看混。

### 第 4 关 · 环环相扣（7×7，12 支箭头，失误上限 2 次）

```
      c0  c1  c2  c3  c4  c5  c6
  r0   ·   v   ·   ·   v   ·   <
  r1   ·   ·   ·   >   ·   v   ·
  r2   ·   ·   ·   ·   ·   ·   ·
  r3   ·   <   ·   ·   ·   ·   ·
  r4   ·   ·   v   ·   ·   ·   <
  r5   ·   ·   ·   ·   ·   <   ·
  r6   <   ·   <   ·   ·   ·   ^
```

通关顺序：`r0c4`(下) → `r3c1`(左) → `r0c1`(下) → `r0c6`(左) → `r5c5`(左) →
`r1c5`(下) → `r1c3`(右) → `r6c0`(左) → `r6c2`(左) → `r4c2`(下) → `r4c6`(左) → `r6c6`(上)

设计意图：本关箭头最多、失误最少。右下角 `r6c6` 被 `r4c6` 和 `r0c6` 两支箭头同时卡住，
必须先把两条互不相干的链都清干净它才走得掉，是全场最后一步。

| 文件 | 作用 |
| --- | --- |

| `实现思路.md` | 实现思路说明：箭头 / 方向 / 关卡的数据表示，以及路径检测方法 |

把逻辑和渲染分开，是为了让“路径判定是否正确”“关卡是否可解”这类问题能脱离图形界面
自动验证——`check_levels.py` 和 `main.py --auto` 都只依赖 `game_logic.py`。

### 动画与视觉反馈

- **飞出**：箭头沿方向加速飞离棋盘，带三层残影拖尾、逐渐淡出，并在原位置溅出火花；
- **碰撞**：箭头朝前顶出去再弹回来（`sin` 曲线），同时由本色渐变到红色、描白边，
  冒出“被挡住了！”的飘字，挡路的箭头被金色方框脉冲闪烁两下；
- **自动提示**：被选中的箭头正常飞出，它的原位套上绿色脉冲圆环、畅通路线画成绿点，
  并飘出“提示：这一支能飞出”。提示动画画在飞出动画的下层，不会挡住箭头；
- 飞出与碰撞动画播放期间会锁住鼠标输入，避免连点导致状态错乱；
- 飘字带半透明底衬，并且靠近棋盘上边缘时会自动改放到格子下方，不会飘出棋盘压到标题。

### 怎么改关卡

编辑 `levels.py`，用字符画描述棋盘即可（`^ v < >` 是箭头，`.` 是空格），
改完跑一遍 `python check_levels.py` 就能确认新关卡有没有解、以及推荐怎么点。
失误上限 `mistakes` 和提示次数 `hints` 也在同一处按关配置（`hints` 不写则用默认值 2）。

## 十、验证情况

`python check_levels.py` 对每一关做五件事，全部通过：

1. 用求解器搜出一条**零失误**的通关顺序（深搜 + 局面去重剪枝）；
2. 把这条顺序通过真正的规则入口 `LevelState.click()` 逐步点一遍，确认每一步都合法、
   最后棋盘清空；
3. 点一支被挡住的箭头，确认箭头**不会消失**、失误次数减一、并返回挡路者坐标；
4. 连续用满提示次数，确认每次给出的箭头都**确实前方畅通**、真的能飞出去（`click` 返回
   `out`）、箭头数减一、**失误次数不变**、提示次数逐次递减、用完后不再给；
   并确认同一局面的提示结果可复现；
5. 调用 `reset()` 后确认箭头数量、失误次数、失误计数、提示次数全部复原；
   连续失误到上限后 `is_failed` 为真。

```
全部 4 关检查通过：均存在零失误通关顺序，且无死局。
```

`python main.py --auto` 则进一步驱动**真实界面代码**（`Game.click_cell`）自动通关：

```
  第 1 关 初识箭头   点击  5 次全部飞出，失误 0 次，界面状态 = win  通过
  第 2 关 连锁反应   点击  8 次全部飞出，失误 0 次，界面状态 = win  通过
  第 3 关 十字路口   点击 11 次全部飞出，失误 0 次，界面状态 = win  通过
  第 4 关 环环相扣   点击 12 次全部飞出，失误 0 次，界面状态 = win  通过
  失误耗尽 -> 失败界面：通过
  自动提示（用 2 次，每次都自动飞出一支、失误不变；第 3 次不再给）：通过
  按 R 重开（游戏中 时按下，局面已打乱）-> 状态 play，箭头 8/8，失误 3/3，提示 2/2
  按 R 重开（通关页 时按下，局面已打乱）-> 状态 play，箭头 8/8，失误 3/3，提示 2/2
  按 R 重开（失败页 时按下，局面已打乱）-> 状态 play，箭头 8/8，失误 3/3，提示 2/2
  「重新开始本关」按钮同样能复原：通过
  飞出动画中按 R 能打断并复原：通过
  R 重开功能总计：通过
```

### 重新开始功能覆盖的场景

「重新开始」在代码里只有一个入口 `Game.restart_level()`，键盘和按钮都走它，
所以三条路径的行为必然一致。`--auto` 里把这几种情况都跑了一遍：

| 场景 | 期望结果 |
| --- | --- |
| 游戏中按 `R` | 箭头、失误次数、提示次数全部复原，动画清空 |
| 通关页按 `R` | 回到游戏界面，本关恢复初始状态 |
| 失败页按 `R` | 回到游戏界面，本关恢复初始状态 |
| 点「重新开始本关」按钮 | 与按 `R` 完全一致 |
| 飞出动画播放中按 `R` | 打断动画并复原，不残留动画对象 |
| 开始界面按 `R` | 无副作用，不报错 |

调试期间这套验证发现过一个真实问题：第 3 关最初把 `r3c5`(下) 和 `r5c5`(上) 摆成了互相
阻挡，形成死局（无论怎么点都清不空）。求解器报出无解后改成了现在的布局。

> 说明：本作业只要求单格箭头的点箭头玩法，未加入额外机关或复杂玩法。

## 十一、附录：清晰度与分辨率

界面按 1000×700 的“设计基准尺寸”编写，**启动时按显示器可用空间自动挑一个缩放倍率**
统一放大（例如 1920×1080 @125% 缩放的屏幕 → 倍率 1.35 → 窗口 1350×945）。
所有尺寸、圆角、线宽、字号都乘以这个倍率，所以放大后是真正按物理像素重绘的，不是把
小图拉大。

这里有个容易踩的坑，也是最初画面发虚的原因：

> Windows 在 125% / 150% 显示缩放下，如果进程**不是 DPI 感知**的，系统会先把窗口按
> 逻辑像素渲染、再**位图拉伸**到物理像素贴到屏幕上。于是 1000×700 的界面被插值放大成
> 1250×875，所有文字和箭头边缘都会发虚——问题不在渲染分辨率，而在于“被系统拉伸”这一步。

所以 `main.py` 在 `pygame.init()` **之前**调用 `SetProcessDpiAwareness(2)` 声明
per-monitor DPI 感知（非 Windows 平台会自动跳过），再用 `SPI_GETWORKAREA` 读取
**物理像素**的屏幕可用区域来挑选倍率。声明之后窗口不再被系统拉伸，每个像素 1:1 映射，
文字与箭头边缘就是锐利的。

倍率会取到 0.05 的整数倍，并保证窗口（含标题栏）放得进屏幕；范围限制在 0.8x ~ 2.0x。
如果自动挑的倍率不合意，用 `--scale` 手动指定即可（例如 `python main.py --scale 1.6`）。
